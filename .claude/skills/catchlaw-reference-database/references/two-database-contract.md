# The Two-Database Contract

The exact ownership split between `reference.db` (content) and `user.db` (record) — tables, file
locations, backup policy, denormalised catch columns, the `user_version` refusal and the ATTACH ban.

## Why two files at all

One sentence: **a content update must never be able to touch the fisher's catch log.** CatchLaw has
no account, no sync and no server, so `user.db` is the ONLY copy of three seasons of trips. A single
fused database makes every rule-pack drop a write against that copy. Two files make it structurally
impossible — the update path only ever calls `File.rename` onto a path the user DB does not live at.

## Ownership matrix

| | `reference.db` | `user.db` |
|---|---|---|
| Nature | content, generated | record, authored by the fisher |
| Produced by | the content CLI at BUILD time | the app at run time |
| Shipped in | `assets/db/reference.db.gz` | nothing is shipped |
| Opened | `readOnly: true` | read-write |
| Migrated | NEVER — `onCreate`/`onUpgrade` throw | forward-only, `run-migration` |
| `schemaVersion` | frozen at `1` | moves; currently `4` |
| Updated by | wholesale replace + atomic rename | `INSERT`/`UPDATE` only |
| Disposable | yes — delete it and it re-extracts | NO — irreplaceable |
| Location | `…/Application Support/reference/` | `…/Application Support/user/` |
| OS backup | EXCLUDED (40 MB, regenerable) | INCLUDED (~200 KB, irreplaceable) |
| Tables | `species`, `zones`, `rules`, `citations`, `content_meta` | `trips`, `catches`, `settings` |
| Rows (v2026.07.14+3) | 3,180 species · 214 zones · 9,412 rules | grows with use |

No table crosses the line. If a new table is neither generated by the content tool nor authored by
the fisher, it is a cache — put it in `user.db` and make it truncatable.

## Directories, and the ones that are wrong

| Candidate | Verdict |
|---|---|
| `getApplicationSupportDirectory()` | **correct** for both, in `reference/` and `user/` subdirs |
| `getApplicationDocumentsDirectory()` | wrong — user-visible on iOS; the fisher can delete the rule pack |
| `getTemporaryDirectory()` | wrong — the OS reclaims it; the app loses its entire rule set at sea |
| Android `getExternalStorageDirectory()` | wrong — other apps and file managers can write to it |
| Asset path directly | impossible — assets are not files; `sqlite3_open` cannot address them |

The cache directory deserves its own line: iOS purges `Library/Caches` under storage pressure WITHOUT
warning and without the app running. For an app whose entire value is answering with no signal, that
is the single worst place the reference DB could live.

Backup exclusion is set once, at install time, on the `reference/` directory:

- iOS — `NSURLIsExcludedFromBackupKey` on the directory URL, via a tiny platform channel
  (see `service-boundary-and-native`).
- Android — `android:dataExtractionRules` / `android:fullBackupContent` excluding
  `files/reference/` in `AndroidManifest.xml`.

## The `catches` row: what is copied and why

A catch row must be able to restate itself, verbatim, three years later, on a build whose rule pack
has retired the rule that produced it. Everything the statement needs is a literal.

| Column | Example | Why literal |
|---|---|---|
| `scientific_name` | `Epinephelus coioides` | the species row may be re-keyed by a content rebuild |
| `common_name` | `هامور  Hamour` | display names are localised content and change |
| `measured_mm` | `380` | the fisher's own observation; never derived |
| `method` | `TL` | `TL`/`FL`/`CW`/`SHL` — a rule change can switch the method |
| `verdict` | `fails` | the conclusion, not recomputed |
| `statement` | `Below the minimum — 38 cm, minimum 45 cm (total length)` | the exact words shown |
| `citation_text` | `Ministerial Decision 580/2015, Art. 3` | instruments are amended and renumbered |
| `citation_published` | `2015-11-03` | provenance |
| `citation_checked` | `2026-07-14` | proves what was known when |
| `content_version` | `2026.07.14+3` | names the pack that produced all of the above |
| `zone_id` | `ae-rak` | Ras Al Khaimah; zone geometry is redrawn between packs |
| `judged_at` | `2026-07-27T05:41:12Z` | when the statement was made |

`species_id` MAY be stored as a soft hint for "show me this species again", but nothing on the record
screen may read through it. If the id no longer resolves, the row still renders completely.

Counter-example to keep in mind: `شعري` Sha'ri (*Lethrinus nebulosus*) carries a closed season
1 Mar – 30 Apr. If a pack later moves that window, a live join would retroactively declare a lawful
March 2025 catch an offence. The denormalised row cannot.

## Refusing a database from the future

Downgrade is real: the fisher sideloads or reinstalls an older APK over a newer one. `user.db` then
has a `user_version` the build does not understand.

| `user_version` on disk | `understoodSchemaVersion` | Action |
|---|---|---|
| absent (new file) | 4 | create at 4 |
| 2 | 4 | migrate forward, 2 → 3 → 4 (`run-migration`) |
| 4 | 4 | open |
| 5 | 4 | **refuse** — throw `UserDbFromTheFutureFailure(found: 5, understood: 4)` |

The refusal screen states both numbers and one route: update the app. It never offers "reset", never
deletes, never renames the file aside. Drift's own `onUpgrade` is not consulted, because reaching it
already means Drift has opened a file with columns it cannot see.

`reference.db` needs no equivalent check: the `INSTALLED` stamp is compared against a compile-time
constant, so an older build simply sees a mismatch and re-extracts its own payload over it.

## The ATTACH ban

`ATTACH DATABASE` and any shared `QueryExecutor` are forbidden. Both re-couple the lifecycles:

- The wholesale swap in a content update renames a NEW file over `reference.db`. Any open handle,
  attached or not, is now pointing at an unlinked inode — statements against the user DB in the same
  connection see a rule set that no longer exists on disk.
- A single connection means one busy-timeout, one WAL, one crash surface. A corrupt reference DB
  would take `user.db` down with it, which is exactly the coupling the split removes.

The rule engine takes plain Dart values. `ReferenceDao` reads rows, maps them to `rule_engine`
records, the engine returns a `Verdict`, and `CatchDao` writes literals. No SQL spans both files.

## Test matrix

| Case | Expectation |
|---|---|
| fresh install | `reference.db` extracted once; `user.db` created at `schemaVersion` 4 |
| content update only | `reference.db` replaced; `user.db` mtime unchanged, row count unchanged |
| app update with schema bump | `user.db` migrated 3 → 4; `reference.db` untouched unless build id moved |
| downgrade | `UserDbFromTheFutureFailure(5, 4)`; file byte-identical after the failed launch |
| delete `reference/` while installed | next launch re-extracts; `user.db` unaffected |
| retire a rule, then open a 2023 catch | row renders its stored `statement` and `citation_text` verbatim |
| any `ATTACH` in `lib/` | `scripts/check_reference_db.sh` fails |
