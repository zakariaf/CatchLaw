## What this delivers

- `app/lib/data/services/user_migration.dart` — the real `MigrationStrategy`: `onCreate`, a
  `stepByStep`-backed `onUpgrade` that toggles `foreign_keys` **outside** the transaction and runs
  `PRAGMA foreign_key_check` after the body, and a `beforeOpen` that re-asserts `foreign_keys = ON` and
  seeds under `details.wasCreated`.
- `app/lib/data/services/user_schema_versions.dart` — generated by `drift_dev schema steps`, committed.
- `app/drift_schemas/user/drift_schema_v1.json` — the committed snapshot for version 1.
- `app/test/drift/generated/` — era-correct classes from `drift_dev schema generate --data-classes
  --companions`, committed.
- `app/lib/data/services/user_database_opener.dart` — `openUserDatabase(File)`: takes the pre-open
  snapshot with checkpoint + `VACUUM INTO` on a raw handle it disposes, opens drift, forces the
  migration with `PRAGMA user_version;`, and on a throw closes, restores by `rename`, and rethrows.
- `app/test/data/user_migration_test.dart` — the shape loop, the v1 content test with a hostile
  fixture, both PRAGMAs, and the forced-throw restore.
- `app/testing/models/user_fixtures.dart` — `kHostileCatch`, `kHostileTrip`: the fixture values every
  migration test writes.

## Why it is built this way

**The harness ships before the first migration does, deliberately.** `user.db` is at version 1, so there
is no `from → to` pair yet — and that is exactly when the harness is cheap to build and impossible to
retrofit under pressure. The every-pair loop is written as a loop over `1..kLatestUserSchemaVersion`, so
it is non-empty the instant E13 or E16 adds a column and nobody has to remember to write it. The v1
content test is not vacuous: it writes hostile rows through the era-correct v1 classes, runs
`migrateAndValidate(db, 1)`, and reads them back — which proves the committed snapshot describes the
live schema, and that is the assertion a CI freshness gate needs.

**A green shape check is necessary and never sufficient.** `migrateAndValidate` compares `CREATE`
statements and reads zero rows: a migration that rebuilds a table perfectly and copies **nothing**
passes it green. `SPEC.md` §7.4 asks for row counts and sample values for exactly this reason, and
`run-migration` rule 7 says it in one line. The content test is the deliverable; the shape test is the
guard rail.

**The fixture is hostile on purpose.** `'test1'` survives everything and proves nothing. The fixtures
carry an apostrophe (`O'Sullivan's mark`), Arabic (`هامور`), an em dash, a backslash, and a
whitespace-only note — the values where a `columnTransformer` or a hand-rolled `INSERT … SELECT` mangles
data silently. Every `expect` carries a `reason:`, because when this fails there is no crash report
coming and the failure message is the entire debugging session.

**The pre-open snapshot uses checkpoint + `VACUUM INTO`, not `File.copy`.** The two skills prescribe
different mechanisms: `run-migration` rule 1 says copy the database file and its `-wal`/`-shm` sidecars
while nothing holds it open; `persistence-drift` rule 10 says never `File.copy` a database and use
`wal_checkpoint(TRUNCATE)` + `VACUUM INTO` + verify-by-reopen. `check-persistence-bans.sh` check 1 fails
any `.copy(` on a line naming a database, and offers no escape hatch — so the executable rule decides,
which is the rule of thumb D-2 records for exactly this shape of disagreement. The intent of
`run-migration` rule 1 is preserved in full: the raw handle used for the checkpoint and the vacuum is
disposed **before** drift opens the file, so nothing is live when the migration runs, and `VACUUM INTO`
produces a single consistent file with no sidecars to keep in step. Restoring is a `rename`, which is
atomic; a restore that could half-succeed would be worse than none.

**Opening is what triggers the migration, so the guard lives at the composition boundary.** The snapshot
must be taken before the open and the restore must happen after the failed connection is closed —
neither can be inside `onUpgrade`, where the file is live. `openUserDatabase` forces the migration with
`PRAGMA user_version;` while the fallback still stands, so a failure is caught at a point where the
snapshot is still valid rather than at some later query.

**None of this is awaited before `runApp`.** `openUserDatabase` is called from inside the `LazyDatabase`
callback, so the snapshot, the migration and the restore all happen on the first query — after the first
frame. `app-startup-and-bootstrap` is explicit that the answer to an unbounded migration is to paint the
UI shell immediately rather than a blank window, and `catchlaw-conventions-index` rule 8 makes it an
invariant. Check 1 of `check_reference_db.sh` proves it mechanically.

**`foreign_keys` is toggled outside the transaction, and checked after the body.** `PRAGMA foreign_keys`
is silently ignored once a transaction is open — a migration that toggles it inside one has simply not
toggled it. It goes off at the top of `onUpgrade`, the steps run in one transaction, then
`PRAGMA foreign_key_check` runs **in production, not only in tests**: a migration that leaves a dangling
reference has lost a record, and SQLite will report it to nobody.

**Rejected: a down migration.** SQLite has none. "Rollback" means restoring the snapshot, and nothing
else. Rejected with it: editing a shipped step — a version-skipping user runs the *edited* step against
old data and loses it — and changing the schema without bumping `schemaVersion`, which means no
migration runs at all on the device and the code and the file diverge in silence.

**Rejected: `eraseDatabaseOnSchemaChange`.** It is a debug convenience that wipes real user data on every
bump. It appears nowhere; `check-persistence-bans.sh` check 3 warns on the string and this task keeps it
absent rather than guarded.

## Tests first

|---|---|---|---|---|
| 1 | `user schema v1 validates against its committed snapshot` | `verifier.startAt(1)`, `migrateAndValidate(db, 1)` | no throw | The freshness gate: a schema changed without regenerating the snapshot fails here |

| 5 | `ar - v1 migration preserves an Arabic species name` | `هامور` | identical | The locale that will break first, and the one §9.4 depends on |
| 6 | `v1 migration preserves a whitespace-only note` | `' '` | `' '`, not `null` and not `''` | The value a "helpful" trim silently destroys |
| 7 | `v1 migration leaves integrity_check reporting ok` | after migrate | `ok` | Corruption that no query notices until the row is read months later |
| 8 | `v1 migration leaves foreign_key_check empty` | after migrate | empty | FKs are off during a migration, so SQLite reports a dangling reference to nobody |

```dart
// app/test/data/user_migration_test.dart
import 'package:catchlaw/data/services/user_database_service.dart';
import 'package:drift/drift.dart';
import 'package:drift_dev/api/migrations.dart';
import 'package:flutter_test/flutter_test.dart';

import 'drift/generated/schema.dart';
import 'drift/generated/schema_v1.dart' as v1;

void main() {
  late SchemaVerifier verifier;

  setUpAll(() => verifier = SchemaVerifier(GeneratedHelper()));

  group('shape', () {
    for (var from = 1; from < kLatestUserSchemaVersion; from++) {
      for (var to = from + 1; to <= kLatestUserSchemaVersion; to++) {
        test('user schema migrates v$from to $to', () async {
          final connection = await verifier.startAt(from);
          final db = UserDatabase(connection);
          addTearDown(db.close);
          await verifier.migrateAndValidate(db, to); // shape only — necessary, not sufficient
        });
      }
    }
  });

  test('user schema v1 validates against its committed snapshot', () async {
    final connection = await verifier.startAt(1);
    final db = UserDatabase(connection);
    addTearDown(db.close);
    await verifier.migrateAndValidate(db, 1);
  });

  test('v1 migration preserves every catch row byte for byte', () async {
    final schema = await verifier.schemaAt(1);

    final old = v1.DatabaseAtV1(schema.newConnection());
    await old.into(old.catchTable).insert(
          v1.CatchCompanion.insert(
            jurisdictionCode: 'ES-GA',
            zoneCode: 'RIAS-BAIXAS',
            speciesId: 7,
            scientificName: 'Epinephelus marginatus',
            outcome: 'meets',
            outcomeDetail: const Value("O'Sullivan\\s mark — 47 cm"),
            createdAt: '2026-07-14T05:41:12Z',
            updatedAt: '2026-07-14T05:41:12Z',
          ),
        );
    await old.close();

    final db = UserDatabase(schema.newConnection());
    await verifier.migrateAndValidate(db, 1);
    expect(
      (await db.customSelect('PRAGMA integrity_check').getSingle()).data.values.first,
      'ok',
      reason: 'corruption here surfaces months later, when the row is read',
    );
    expect(await db.customSelect('PRAGMA foreign_key_check').get(), isEmpty,
        reason: 'migration left a dangling reference — a lost record');
    await db.close();

    final now = UserDatabase(schema.newConnection());
    addTearDown(now.close);
    final rows = await now.select(now.catchTable).get();
    expect(rows, hasLength(1), reason: 'a row disappeared during migration');
    expect(rows.single.outcomeDetail, "O'Sullivan\\s mark — 47 cm",
        reason: 'an apostrophe and a backslash must survive intact');
  });

  // … one test per remaining row above, one behaviour each
}
```

## Implementation outline

1. Generate and commit the snapshot artefacts, from `app/`:
   ```bash
   dart run drift_dev schema dump lib/data/services/user_database_service.dart drift_schemas/user/
   dart run drift_dev schema generate --data-classes --companions \
     drift_schemas/user/ test/drift/generated/
   dart run drift_dev schema steps drift_schemas/user/ lib/data/services/user_schema_versions.dart
   ```
   `--data-classes --companions` is load-bearing: without it only shape tests are possible, because
   nothing can write a row in the v(n) world and read it in the v(n+1) world.
2. Move the `MigrationStrategy` out of T04's `user_database_service.dart` into `user_migration.dart`
   and give it the real shape: `onCreate: (m) => m.createAll()`; `onUpgrade` that runs
   `PRAGMA foreign_keys = OFF` **before** `transaction(() => _steps(m, from, to))` and
   `PRAGMA foreign_key_check` after it, throwing on any orphan; `beforeOpen` that re-asserts
   `foreign_keys = ON` and seeds under `details.wasCreated`.
3. Declare `final _steps = stepByStep();` with no branches yet, and `const kLatestUserSchemaVersion =
   UserDatabase.understoodSchemaVersion;` so the loop and the version stay one fact.
4. Write `openUserDatabase(File)`: if the file exists, open a raw handle, `PRAGMA
   wal_checkpoint(TRUNCATE)`, `VACUUM INTO '<path>.premigration'`, dispose the handle; then construct
   the drift database, force the migration with `await db.customStatement('PRAGMA user_version;')`, and
   delete the snapshot on success. On a throw: `await db.close()`, delete the live file, `rename` the
   snapshot into place, rethrow.
5. Write `user_fixtures.dart` with the hostile constants, `k`-prefixed per `CONVENTIONS.md` §6.
6. Add a CI step that re-runs the three `drift_dev schema` commands and fails on a dirty tree, so a
   schema change without a regenerated snapshot cannot merge.
7. Re-run the suite. 15 green, and T04's 18 still green.
